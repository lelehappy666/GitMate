# 提交图刷新、完整性校验与双布局设计

## 1. 背景

GitMate 的提交图已经支持无限画布、提交节点拖动、分组折叠、版本区域、固定端口以及曲线和直角连线。新的目标是在不破坏这些能力的前提下，补齐主动刷新、数据完整性校验和大仓库浏览能力，并增加类似 GitKraken 的传统分支图。

现有实现经过代码与真实仓库审计后确认：

- 当前仓库共有 145 个唯一提交和 144 条父子关系，没有缺失端点。
- 当前 Git 查询覆盖全部本地分支和远程分支，并按完整哈希去重。
- 使用 405 个提交的隔离仓库验证分页算法后，分页拼接可覆盖全部 405 个提交，没有重复或遗漏。
- 当前刷新只读取最早端的首个 200 条提交，较新的提交依赖向下浏览后继续加载。因此，大仓库刷新后可能暂时看不到最新提交，容易被误认为数据缺失。
- 从其他页面进入提交图时会执行页面任务；但已经停留在提交图时再次点击侧边栏按钮，路由没有变化，不会再次触发刷新。
- 当前布局在处理每个提交时会扫描已分配的全部历史节点，规模增大后接近 O(N²)。
- 当前场景投影和 Canvas 绘制仍会遍历完整节点与连线集合，再逐项判断是否可见；节点拖动也会重新投影全图。该方式无法稳定支持 50,000 个提交。

## 2. 目标

本次设计需要实现：

1. 提交图工具栏提供刷新按钮。
2. 每次点击侧边栏“提交图”都触发刷新，包括当前已经位于提交图的情况。
3. 每次刷新校验全部本地和远程分支中的提交、父子关系和分支指针，明确报告是否存在缺失。
4. 刷新只同步 Git 数据变化，不重置视口、缩放、手动位置、分组、折叠状态、固定端口和版本区域。
5. 逻辑层完整支持 50,000 个提交，交互和绘制工作量与当前可见内容相关。
6. 提供“传统布局”和“画布布局”切换。
7. 传统布局采用类似 GitKraken 的分支泳道，最新提交在上、最早提交在下。
8. 画布布局保持最早提交在上、最新提交在下，并继续支持自由编辑。

## 3. 非目标

- 不修改 Git 仓库内容，不执行 fetch、pull、reset 或其他写操作。
- 不把 Stash、工作区未提交变更混入提交图。
- 不为直角连线增加自动避障。
- 不允许传统布局拖动提交节点。
- 不改变现有分组禁止嵌套、端口固定和区域标识规则。
- 不引入新的数据库或第三方图形框架。

## 4. 架构边界

提交图拆分为三个数据层，每层只有一个明确职责。

### 4.1 `CommitGraphSnapshot`

这是 Git 数据的唯一真值，包含：

- 仓库身份与规范化本地路径；
- 本地分支、远程分支及其指针；
- HEAD 与默认分支信息；
- 提交记录、完整哈希、父哈希和装饰信息；
- 唯一提交数、关系数、浅克隆状态；
- 引用指纹、快照版本和生成时间；
- 最近一次完整性报告。

提交和边以完整哈希作为稳定身份。任何 UI 布局都不能修改这份拓扑数据。

### 4.2 `CommitGraphSceneState`

这是用户编辑状态的唯一真值，继续保存：

- 普通节点手动位置；
- Group 的唯一 `origin` 和成员相对坐标；
- 分组名称、成员和折叠状态；
- 版本区域的位置、尺寸、名称和颜色；
- 普通边固定端口和跨组边固定端口；
- 画布线型与画布视口；
- 仓库上次选择的布局模式。

场景状态不保存父子关系，不产生第二份 Git 拓扑真值。

### 4.3 `CommitGraphRenderIndex`

这是由快照和场景派生的运行时索引，包含：

- 哈希到提交、节点和相邻边的索引；
- 使用真实场景位置构建的空间索引；
- 传统布局的可见行索引；
- 当前视口及预加载区域中的节点和边；
- 已生成路径的缓存；
- 当前语义缩放级别。

该索引不作为持久化真值。拓扑变化时重建受影响部分；拖动节点或 Group 时只更新目标、成员、相邻边和相关空间桶。

## 5. 刷新触发与并发控制

### 5.1 刷新入口

刷新有两个等价入口：

- 提交图工具栏的“刷新”按钮；
- 侧边栏的“提交图”按钮。

侧边栏不能只依靠路由值变化。每次点击都递增一个仓库级 `refreshRevision`，即使路由仍是同一个提交图，页面任务也会根据新 revision 执行刷新。首次进入页面同样执行刷新。

### 5.2 请求协调

`CommitGraphRefreshCoordinator` 负责：

- 同一仓库短时间内的重复刷新合并；
- 取消已经过期的扫描任务；
- 使用递增请求编号隔离结果；
- 只允许最新请求替换快照；
- 保持旧快照可见，避免刷新期间清空画布；
- 将读取、解析、布局和校验放在主线程之外。

## 6. 快照缓存与引用指纹

### 6.1 本地缓存

新增独立的 `CommitGraphSnapshotStoring` 接口和文件实现。缓存位于应用支持目录的提交图快照子目录，以仓库 ID 分文件保存。缓存使用带 schema version 的紧凑二进制 Property List，不引入第三方数据库。

写入顺序为：

1. 完成 Git 扫描；
2. 生成逻辑图；
3. 完成完整性校验；
4. 写入同目录临时文件；
5. 原子替换上一次正确快照。

缓存损坏、版本不兼容、仓库身份不匹配或路径已指向其他仓库时，缓存会被忽略并重新构建。

### 6.2 指纹

引用指纹由排序后的本地分支、远程分支、HEAD、默认分支、指针哈希和浅克隆状态共同生成。刷新时先读取指纹：

- 指纹未变化：复用当前快照和布局，只重新执行内存完整性检查并更新时间。
- 指纹变化：后台重新扫描当前全部可达提交，生成候选快照并对账。

指纹只是跳过无效重算的优化，不能代替完整性校验。

## 7. Git 数据扫描与完整性校验

### 7.1 扫描范围与顺序

扫描范围包括全部 `refs/heads/*` 和 `refs/remotes/*` 可达提交。相同提交被多个分支引用时只保留一个节点。Git 拓扑顺序是唯一排序依据；作者时间只用于显示，不能决定父子前后关系。

扫描完成前快照状态为“正在构建”，不能把部分页面标记为完整。缓存不存在时，页面显示构建进度；缓存存在时继续显示上一次正确图。

### 7.2 完整性报告

新增纯数据结构 `CommitGraphIntegrityReport`，至少包含：

- Git 报告的唯一提交数；
- 快照节点数；
- 预期父子关系数；
- 实际关系数；
- 重复提交哈希；
- 重复关系 ID；
- 缺失父节点；
- 悬空边；
- 缺失分支顶点；
- 拓扑顺序错误；
- 浅克隆历史边界；
- 总体状态和检查时间。

校验规则如下：

1. `rev-list` 的唯一提交总数必须等于快照节点数。
2. 每个完整提交哈希只能对应一个节点。
3. 每个本地和远程分支指针必须指向图中存在的提交。
4. 对每条提交记录中的每个父哈希，若父提交在可达集合中，必须存在且只存在一条对应关系。
5. Merge 提交的全部父边都必须保留；第一父边和额外 Merge 父边的语义不能混淆。
6. 每条边的两个端点必须存在。
7. 父提交在画布顺序中必须早于子提交，在传统顺序中必须晚于子提交。
8. 浅克隆边界外的父哈希显示为历史边界，不作为损坏或缺失。

首次校验失败后，协调器绕过缓存完整重读一次。第二次仍失败时保留上一次正确快照，不允许候选数据替换当前画布。

## 8. 刷新后的场景对账

候选快照校验通过后，使用完整哈希进行场景对账：

- 未变化的提交保留手动位置、分组成员关系和固定端口。
- 未变化的边继续复用原有 `side` 和 `offset`。
- 新提交进入逻辑图，并由对应布局引擎分配初始位置。
- 不可达提交、选择状态和相邻边被移除。
- Group 先移除不存在的成员；剩余成员不足两个时安全解散，剩余节点恢复为普通节点。
- 只重建聚合键发生变化的 Group 端口；聚合键不变的端口继续复用。
- 版本区域、缩放、视口、布局模式和折叠状态保持不变。
- 当前详情对应的提交消失时关闭详情，并说明该提交已不在当前分支历史中。

刷新不会调用“自动布局”，也不会移动已有节点。

## 9. 双布局模式

页面顶部提供分段按钮：

- `传统布局`
- `画布布局`

布局选择按仓库保存。首次默认使用传统布局。两种布局共用同一快照、完整性报告、搜索条件、分支聚焦和当前选中提交，切换布局不会重新读取 Git。

由于两个布局的时间方向相反，切换后不保留相同的纵向滚动百分比，而是将当前选中提交居中；没有选中提交时聚焦当前分支 HEAD。

### 9.1 传统布局

传统布局采用类似 GitKraken 的固定提交行和分支泳道：

- 最新提交在最上方，最早提交在最下方。
- 默认分支按 `origin/HEAD`、当前 HEAD、`main`、`master` 的顺序识别。
- 主分支固定在第一条核心泳道。
- 功能分支在相邻泳道展开，分叉时创建泳道，Merge 后释放不再使用的泳道。
- 泳道颜色由稳定分支身份生成，刷新后不得无故变色或换列。
- 左侧显示泳道、节点、分叉和 Merge，右侧显示标题、作者、时间、哈希、分支与 Tag。
- Merge 提交必须显示全部父边。
- 泳道过多时只让泳道区域横向滚动，提交信息区域保持可读。
- 提交行使用虚拟列表，只创建当前窗口及少量预加载行。
- 传统布局不允许拖动节点。
- 画布 Group 在传统行中显示成员标识，但折叠、重命名、增删成员和区域编辑仍在画布完成。

传统泳道布局使用活动泳道算法，目标复杂度为 O(N+E)，不能为每个提交扫描全部历史节点。

### 9.2 画布布局

画布布局保持既有交互和方向：

- 最早提交在上，最新提交在下。
- 支持自由平移、缩放、节点拖动、Group 拖动、折叠、区域和固定端口。
- 自动布局和聚焦主分支只改变派生布局或视口，不改变分组和折叠状态。
- 普通节点和 Group 继续使用矢量绘制。
- 直角连线继续按端点方向伸出 28px 后使用中线法连接，不增加自动避障。

画布布局同样使用线性拓扑布局，不再使用接近 O(N²) 的历史列扫描。

## 10. 50,000 提交的渲染策略

### 10.1 真正的可视区域裁剪

逻辑图始终包含全部提交，但渲染层只查询：

- 当前可见窗口；
- 上方约 1.5 个窗口；
- 下方约 1.5 个窗口；
- 与这些节点相连且可能穿过视口的边。

Canvas 不再遍历完整 `projection.nodes` 和 `projection.edges` 后逐项裁剪。空间索引使用场景中的真实位置，而不是只使用初始自动布局位置。

### 10.2 局部更新

- 节点拖动只更新该节点、其空间桶和相邻边路径。
- Group 拖动只更新 Group、成员节点和边界边。
- 区域拖动或缩放只更新对应区域。
- 滚轮、触控板、拖动和缩放事件继续使用 `requestAnimationFrame` 合并。
- 路径缓存键至少包含边身份、端点位置版本、端口和线型。
- 切换线型只重新生成当前可见路径，不修改端口。

### 10.3 语义缩放

- 80%–200%：完整提交卡片，显示标题、作者、哈希和分支。
- 50%–80%：精简卡片，显示标题、短哈希和关键标识。
- 35%–50%：节点圆点和分支泳道，保留分叉、Merge、Tag、Group 与区域轮廓。

所有档位继续使用矢量绘制。低缩放档位只是减少文字和装饰，不删除逻辑节点或关系。

## 11. 导航与视觉焦点

### 11.1 历史导航条

画布右侧增加纵向历史导航条：

- 顶部表示初始提交，底部表示最新提交；
- 显示当前主画布视口范围；
- 标记分支顶点、Tag、版本区域和 Group；
- 支持拖动视口指示器快速跳转。

当提交数量过大时，“适配全部”不再尝试把 50,000 张卡片压缩到主画布，而是打开全局历史概览，再由用户选择要查看的区域。

### 11.2 搜索与快速跳转

提交搜索支持：

- 标题；
- 完整或短哈希；
- 作者；
- 分支；
- Tag。

快捷入口包括初始提交、最新提交、当前分支和指定 Tag。选中提交时强化直接父子关系和 Merge 路径，其他关系降低透明度，形成清晰视觉焦点。

## 12. 页面状态与错误处理

工具栏显示刷新按钮、最后刷新时间和完整性摘要：

- 绿色：`已校验 · 50,000 个提交 · 52,418 条关系`；
- 黄色：正在刷新、使用缓存或存在浅克隆历史边界；
- 红色：节点、关系或分支指针不一致，可展开查看具体哈希。

异常规则：

- 刷新失败且存在旧快照：继续显示旧图，提示“刷新失败，显示上次正确结果”。
- 首次打开且无法读取 Git：显示明确错误、仓库路径和重试按钮。
- 仓库在刷新中被移动或删除：取消任务，不改写缓存和当前画布。
- 缓存损坏：忽略缓存并重新扫描。
- 历史重写或强制推送：完整对账后再移除不可达节点。
- 浅克隆边界：显示黄色说明，不误报为数据损坏。

## 13. 性能验收

以 Release 构建和包含 50,000 个提交、多个分支及 Merge 的固定仓库为基准：

- 指纹未变化的刷新不得重新执行完整 Git 日志解析或布局。
- 缓存存在时先显示正确的旧快照，再执行后台校验。
- 完整扫描、解析和布局不得长时间占用主线程。
- 平移、缩放和拖动的主线程帧工作以 60 FPS 为目标。
- 视口查询与渲染准备只与可见节点和可见边数量相关。
- 拖动节点不得触发完整拓扑、完整分组或完整端口重算。
- 传统列表滚动不得同时创建全部 50,000 个行视图。

性能测试记录缓存读取、指纹读取、完整扫描、布局、完整性校验、视口查询、首帧和拖动帧耗时，不能只依赖人工观察。

## 14. 测试范围

### 14.1 Git 读取与完整性

- 全部本地和远程分支提交读取与去重；
- 最早到最新和最新到最早两种稳定拓扑顺序；
- 普通父边、分叉和多父 Merge；
- 分页或分批解析拼接不重复、不缺失；
- 提交数不一致、重复节点、重复边、悬空边和缺失分支顶点；
- 浅克隆边界不误报。

### 14.2 刷新与场景对账

- 指纹不变时不重复布局；
- 指纹变化时正确新增和删除提交与关系；
- 重复点击当前侧边栏按钮仍触发刷新；
- 手动刷新和侧边栏刷新使用同一协调器；
- 旧任务不能覆盖较新结果；
- 刷新后视口、分组、折叠、区域、手动位置和稳定端口不变；
- 被删除成员的 Group 安全修复；
- 校验失败时不替换旧快照。

### 14.3 传统布局

- 最新提交在上、最早提交在下；
- 主分支核心泳道稳定；
- 分叉创建新泳道，Merge 后正确释放；
- 全部 Merge 父边存在；
- 刷新后泳道和颜色稳定；
- 50,000 个提交只返回可见和预加载行；
- 横向泳道滚动不影响提交信息区域。

### 14.4 画布与双布局

- 空间索引使用真实场景位置；
- 可视区域查询只返回窗口和预加载内容；
- 三档语义缩放选择正确；
- 节点拖动只更新目标与相邻边；
- 路径缓存失效范围正确；
- 切换布局后聚焦相同选中提交；
- 两种布局共用快照、搜索和完整性报告；
- 切换传统布局不能修改画布 Group、区域和手动位置。

### 14.5 缓存与恢复

- 快照原子写入与读取；
- schema 迁移和不兼容缓存处理；
- 损坏缓存自动回退完整扫描；
- 仓库身份和路径不匹配时拒绝复用；
- 刷新失败、仓库移动和任务取消后保留最后正确结果。

## 15. 预计代码边界

实现时优先复用当前技术栈，并将职责控制在以下边界：

- `LocalGitReading`：增加引用指纹和完整快照读取能力；
- `CommitGraphSnapshot`、`CommitGraphIntegrityValidator`：Git 真值与纯校验函数；
- `CommitGraphSnapshotStore`：版本化原子缓存；
- `CommitGraphRefreshCoordinator`：刷新合并、取消和候选快照提交；
- `CommitGraphTraditionalLayout`：活动泳道和传统行模型；
- `CommitGraphCanvasLayout`：父提交优先的线性画布布局；
- `CommitGraphRenderIndex`：真实位置空间索引和局部更新；
- `CommitGraphViewModel`：页面状态编排，不直接承担 Git 解析或绘制算法；
- `CommitGraphView`：刷新状态、布局切换和公共工具栏；
- 独立传统布局视图与现有画布视图：共享选择和详情，不共享展示状态。

不进行与提交图无关的页面重构。
