# 传统提交主干专属与分支独占泳道设计

## 背景

当前传统提交图虽然将 `main` 的逻辑槽位排在最左侧，但提交归属仍优先受当前 HEAD 和原始拓扑泳道影响。共享历史可能继承功能分支的归属或颜色，导致非 `main` 分支看起来占用了最左侧主干。多个引用指向同一提交时，附加引用连线也可能被误解为分支共用泳道。

本轮只调整传统布局的分支投影、提交归属和连线表达，不修改画布式布局、Git 数据读取、提交详情以及工作区未提交摘要的业务范围。

## 目标

1. 第 0 泳道永久保留给逻辑 `main` 主干。
2. 本地 `main` 或任意远程 `<remote>/main` 存在时，由逻辑 `main` 使用第 0 泳道。
3. 本地和远程均不存在 `main` 时，第 0 泳道保持空白；任何其他分支都不能递补到最左侧。
4. 每个非主干逻辑分支独占一条泳道，不得借用或延续其他分支的竖线。
5. 分叉、合并和共享祖先关系只通过明确的跨泳道连线表达。
6. 本地分支与对应远程跟踪分支在历史可线性衔接时视为同一逻辑分支：远程已知部分使用实线，本地领先部分使用虚线。
7. 本地与远程同名分支已经真正分叉时，不强行压入同一竖线；它们使用相邻泳道，并在共同祖先处建立连接。
8. 维持大量提交和大量分支下的局部查询与虚拟化能力。

## 非目标

- 不复制同一个提交节点来为每个可达分支生成完整历史副本。
- 不把 Git 分支理解为提交的永久唯一所有者。
- 不改变“最新提交在上、最早提交在下”的传统布局方向。
- 不改变工作区未提交记录的独立摘要展示。
- 不为直角或曲线连线增加自动避障。

## 核心模型

### 逻辑分支

逻辑分支是传统布局的泳道单位：

- `main` 与可线性衔接的 `origin/main`、`upstream/main` 归入逻辑 `main`；
- 本地 `<name>` 与同名远程 `<remote>/<name>` 在提交拓扑可线性衔接时归入同一逻辑分支；
- 只有本地或只有远程的引用分别形成独立逻辑分支；
- detached HEAD 与 synthetic 分支始终使用真实 ID，禁止因展示名称相同而合并；
- 同名本地和远程引用若双方 tip 互不可达，则视为已经分叉，拆成相邻但独立的逻辑分支。

“可线性衔接”指两个 tip 相同，或任意一个 tip 是另一个 tip 的祖先。该判断直接使用完整提交快照，不依赖名称猜测来掩盖真实分叉。

### 泳道编号

- 第 0 泳道是保留槽位，标识固定为 `main`。
- 存在逻辑 `main` 时，它固定映射到第 0 泳道。
- 不存在逻辑 `main` 时，投影仍产生一个空主干槽；其他逻辑分支从第 1 泳道开始。
- 其他泳道按当前 HEAD、是否本地、最近活动时间和稳定 ID 排序，排序结果在同一快照内保持稳定。
- 横向滚动、视口裁剪和分割线拖动只改变可见范围，不改变泳道编号。

### 提交归属区段

传统布局不再先到先得地把整条第一父链交给当前 HEAD。新的归属规则为：

1. 先为逻辑 `main` 建立主干基准路径；主干上的提交节点和竖向连接始终绘制在第 0 泳道。
2. 再为每个非主干分支计算从 tip 到首个已归属共同祖先之间的独有区段。
3. 独有区段全部绘制在该分支自己的泳道。
4. 分支到共同祖先只生成一条跨泳道连接，分支竖线在连接点结束。
5. Merge 提交的非第一父边继续作为跨泳道合并连接，不改变任一分支的泳道归属。
6. 没有 `main` 时，第 0 泳道不承载提交；第一个非主干分支在第 1 泳道建立自己的基准路径。

共享提交只绘制一次，归属于确定的基准路径；其他能够到达该提交的分支通过关系线连接，不复制节点。

## 绘制规则

### 节点与竖线

- 圆形表示提交节点。
- 同一逻辑分支的连续提交使用同一条固定 X 坐标的竖线。
- `main` 的节点和主线颜色固定，不继承当前 HEAD 或旧拓扑泳道颜色。
- 非主干分支使用其逻辑分支的稳定颜色，颜色与顶部标签保持一致。
- 远程可达的提交和连接使用实线。
- 仅本地可达的已提交记录使用同色虚线，并保留“未推送”标识。

### 分叉与合并

- 分支从共同祖先产生时，由主干或基准分支节点连向该分支首个独有提交。
- 分支合并回其他分支时，由 merge 提交连向对应父提交。
- 交叉但没有节点的线不表示合并；绘制层应尽量避免制造无意义的长水平引用线。
- 本地与远程 tip 相同的额外引用使用紧贴提交节点的引用徽标，不再通过横跨多个泳道的水平线表达。

### 空主干

仓库不存在任何 `main` 引用时：

- 顶部第一个槽仍显示“main（不存在）”或等价的弱化占位；
- 第 0 泳道不绘制竖线、节点或引用标记；
- 其他分支从第 1 泳道开始，确保视觉位置不会因仓库当前状态改变而冒充主干。

## 数据流与组件边界

1. `CommitGraphBranchCatalog` 继续描述真实 Git 引用及其可达关系，但不再负责最终传统泳道的提交所有权。
2. `CommitGraphTraditionalBranchProjector` 负责逻辑分支配对、分叉判断、主干占位与稳定泳道编号。
3. 新的传统区段投影纯函数根据完整快照和逻辑分支生成：提交到泳道映射、分支区段、分叉连接、合并连接和引用徽标。
4. `CommitGraphTraditionalLayout` 消费区段投影生成可见行与连接索引。
5. `CommitGraphTraditionalCanvas` 只读取最终泳道和稳定颜色，不再通过 `branchCatalog.branch(containing:)` 临时重判提交泳道。
6. 发布状态索引继续独立提供实线与虚线判定，避免绘制阶段遍历提交图。

## 性能约束

- 完整快照变化时计算一次祖先关系、逻辑分支和区段归属。
- 滚动、缩放、分割线拖动和选择提交不得重新计算拓扑或分支区段。
- 绘制阶段对提交泳道、发布状态和可见连接保持 O(1) 查询。
- 50,000 个提交和数百个引用下仍只创建可见行的头像与信息视图。

## 迁移与兼容

- 现有分割线宽度、传统布局选择、场景 Group、Region、折叠状态和视口设置保持不变。
- 本轮无需提高场景 schema；新的泳道与区段投影是完整快照的可重建派生数据。
- 旧缓存加载后使用新投影重新生成传统布局，不修改 Git 仓库内容。

## 测试设计

至少覆盖以下纯函数和集成行为：

1. 本地 `main`、仅 `origin/main` 以及两者同时存在时，第 0 泳道均为逻辑 `main`。
2. 完全没有 `main` 时，第 0 泳道为空，其他分支从第 1 泳道开始。
3. 可线性衔接的本地与远程同名分支共用逻辑泳道。
4. tip 互不可达的同名本地与远程分支拆为相邻独立泳道。
5. 每个非主干分支的独有提交始终位于自己的泳道。
6. 共享祖先只绘制一次，分支通过连接进入共同祖先。
7. Merge 的非第一父边生成关系线，但不改变节点泳道。
8. 主干颜色与顶部 `main` 标签一致，不受当前 HEAD 影响。
9. 远程已知提交为实线，本地领先提交为虚线。
10. 多分支、无 main、detached、synthetic、浅克隆边界和大量提交性能回归。

## 验收标准

- 任何仓库中，只有逻辑 `main` 可以使用最左侧第 0 泳道。
- 没有 `main` 时，最左侧泳道可见为空，其他分支不会左移递补。
- 任意非主干分支的竖线只承载自己的独有提交区段。
- 分支之间的拓扑关系能够通过明确连线追踪，节点不重复、不丢失。
- 本地与远程状态、颜色、分支标签和实际提交关系一致。
- 完整测试、Debug/Release 构建和重新打包全部通过后才交付。
