# 提交图统计、状态与分层组织树设计

## 1. 背景与目标

本次修正提交图的三类问题：

1. 传统布局顶部的分支数量和引用数量口径不清晰，符号引用、合成分支与可操作分支被混合计数。
2. 提交图顶部的完整性、刷新状态在窗口变窄时被压缩，文字会换行、裁剪，甚至只剩图标。
3. 画布现有布局只是将稳定泳道交替放到主干两侧，没有根据完整子树宽度和拓扑层级排列，因此会出现节点重叠、连线穿过无关节点、多分支难以阅读的情况。

目标是在不改变 Git 真实拓扑、分组、折叠、版本区域和手动位置语义的前提下，提供准确统计、单行状态栏和 XMind 式的自上而下分层组织树。

## 2. 非目标

- 不改变 Git 日志的读取范围、完整性校验和快照缓存协议。
- 不将同一提交复制到多个分支子树中。
- 不允许自动布局解散 Group、展开已折叠 Group 或删除版本区域。
- 不在滚动、缩放或每帧绘制时重算 Git 拓扑、分支身份或发布状态。

## 3. 分支和引用统计

### 3.1 逻辑分支

界面主统计显示“`N 个逻辑分支`”。逻辑分支名称的归一化规则为：

- `refs/heads/<name>` 归一化为 `<name>`。
- `refs/remotes/<remote>/<name>` 归一化为 `<name>`。
- 本地与任意远程的同名分支合并为一个逻辑分支，包括两端提交已经分叉的情况。
- 本地 `main` 与 `origin/main` 必须是同一个逻辑分支。
- `origin/HEAD` 等带 `symbolicTarget` 的符号引用不是分支，不计入。
- `Detached HEAD`、“未命名分支”等内部合成描述不计入用户分支数。

分支标签仍保留它所包含的所有本地和远程引用，例如 `main +1`表示同一逻辑分支下还有一个直接引用。

### 3.2 直接 Git 引用

第二个统计显示“`M 个直接引用`”，只计算不带 `symbolicTarget` 的 `refs/heads/*` 和 `refs/remotes/*/*`。符号引用依然留在快照中用于默认分支识别，但不进入数量和分支卡片。

统计数据由 Core 层的纯函数投影产生，SwiftUI 只消费结果，不自行过滤或推断。

## 4. 本地与云端状态

对每个提交预构建以下三态：

| 状态 | 判定 | 连接线 | 节点边框 | 附加标识 |
| --- | --- | --- | --- | --- |
| 本地与云端一致 | 同时可从本地和任意远程分支到达 | 实线 | 实线 | 无 |
| 本地独有 | 只可从本地分支到达 | 虚线 | 虚线 | 无 |
| 云端独有 | 只可从远程分支到达 | 虚线 | 虚线 | Cloud 图标 |

一个提交同时被多个逻辑分支共享时，只要它同时存在本地和远程可达集合中，就使用“一致”状态。线型和节点边框始终使用同一份状态投影，禁止分别推断造成视觉矛盾。

## 5. 顶部状态栏

完整性状态和刷新状态使用独立的单行胶囊：

- 图标、文字和内边距作为一个不可拆分的水平单元。
- 文字设置为单行，禁止换行，不会只剩图标。
- 窗口宽度不足时，优先收缩搜索框；仍然不足时，将低优先级文字收入“更多”菜单，不压缩状态胶囊。
- 刷新按钮始终保留稳定的点击区域，刷新中用进度图标替换内容时不改变按钮尺寸。

## 6. 分层组织树布局

### 6.1 时间和拓扑方向

- 最早的初始提交在最上方，最新提交在最下方。
- 每条父边的父提交必须位于子提交上方。
- 层级使用从根提交出发的最长路径深度，同一层只放置没有直接父子关系的节点。
- `main` 的共享历史是主组织树骨架；其他分支在真实分叉点下生成子树，Merge 在真实合并节点回连。

### 6.2 子树宽度和间距

布局分两趟计算：

1. 自底向上计算每个节点或折叠分支摘要的子树宽度。
2. 自上向下在父节点的子树区间中居中放置，兄弟子树按稳定分支身份排序。

间距扩大为现有画布的 2 倍：

- 水平节点中心间距默认为 500 px。
- 垂直层级中心间距默认为 252 px。
- 子树边界额外保留至少 56 px 安全间距，卡片、Group、分支摘要和版本区域不得重叠。

### 6.3 大量分支和折叠摘要

- `main`、当前 HEAD 分支和 Merge 关键节点始终展开。
- 非当前分支连续提交超过 12 个时，默认折叠为分支摘要节点，显示分支名、提交数和时间范围。
- 点击摘要节点在原位展开完整子树，再次点击折叠。
- 搜索、历史导航或选中命中折叠成员时，只临时展开目标所在分支，不改变其他分支。
- 折叠状态按稳定分支身份保存，刷新、缩放和拖动不会丢失。

## 7. 连线端口和避障

### 7.1 固定端口

- 组织树的普通父子边默认从父节点底部端口出发，进入子节点顶部端口。
- Merge 边使用靠近目标子树的左或右固定端口。
- 端口一经分配，移动节点、切换线型、缩放和平移不会改变 `side` 和 `offset`。

### 7.2 不接触无关节点

自动布局产生的每条边只能与自己的起点和终点卡片接触。所有其他节点、分组和分支摘要都是障碍物，连线必须保留至少 28 px 的净空距离。

布局阶段为每对相邻层级预留水平走线通道，并为每个子树预留垂直边界通道。路径生成顺序为：

1. 从端口按方向伸出 28 px。
2. 在父子层之间的专用通道中水平移动。
3. 在目标子树的专用垂直通道中向下移动。
4. 进入终点端口前再保留 28 px 直线段。
5. 删除重复点和连续共线点。

若 Merge 边跨越多个子树，则使用子树包围盒外侧的稳定迂回通道。通道索引由边的稳定 ID 决定，刷新后不会无故换路。

直角线使用上述折线；曲线将同一条无碰撞折线的转角替换为圆角三次贝塞尔过渡，不改变通道和端点。

## 8. 场景、刷新与手动位置

- 新布局使用新的画布算法版本。旧场景首次打开时，只对没有手动移动、没有属于 Group 的节点应用组织树坐标。
- 手动移动过的节点、Group `origin` 和成员相对坐标保持不变。
- “自动布局”只重排未分组的普通节点和分支摘要；保留 Group、折叠、Region、线型和视口状态。
- Git 刷新时先构建新的完整拓扑和组织树默认坐标，再与当前场景对账；旧代结果不得覆盖新代场景。

## 9. 性能与虚拟化

- 分支归一化、本地/云端可达集合、层级、子树宽度、默认端口和走线通道只在快照变化或用户执行“自动布局”时计算。
- 屏幕绘制继续使用空间索引和局部可见查询，不遍历全部节点和边。
- 折叠分支只为摘要节点生成绘制几何，内部节点和边不进入可见索引。
- 节点拖动继续使用显示帧合并更新；拖动时只更新节点坐标、关联边路径和局部空间索引。

## 10. 错误处理

- 无有效 Git 快照时保留现有错误页，不构建空的伪分支树。
- 发布状态只基于当前快照中已知的本地和远程引用；不主动执行 `git fetch`。
- 浅克隆边界继续使用独立边界端点，不把缺失父提交误判为本地或云端独有提交。
- 若障碍物将常规通道完全占用，则稳定向子树包围盒外侧扩展通道，不允许降级为穿过节点。

## 11. 测试与验收

### 11.1 统计和状态

- 本地与远程同名分支只计一个逻辑分支。
- 分叉后的同名本地/远程分支仍只计一个。
- `origin/HEAD` 和合成分支不计入分支数和直接引用数。
- 一致、本地独有、云端独有三种状态判定正确。
- 连线和节点边框始终使用同一线型，只有云端独有节点显示 Cloud。

### 11.2 分层组织树

- 最早提交在最上，最新提交在最下，所有父节点位于子节点上方。
- 直线、分叉、多分支、Merge、Octopus Merge、多根历史和浅克隆边界均不丢失节点或边。
- 任意两个可见卡片不重叠，水平和垂直中心间距符合 500/252 px 默认值。
- 每条边除自己的起点和终点外，不与任何其他节点或分支摘要相交，并保留至少 28 px 净空。
- 曲线/直角切换不改变端口和通道。
- 超过 12 个连续提交的非当前分支默认折叠，展开后恢复所有节点和边。

### 11.3 界面和性能

- 顶部状态在常用窗口宽度下保持单行，不只显示图标。
- 刷新按钮在普通/刷新中两种状态下尺寸一致。
- 50,000 提交、300 分支下，分层和子树布局仍为快照级一次派生，每帧查询工作量只与可见元素数量相关。
- 全量核心测试、Debug 构建、Release 构建、应用签名和 ZIP 完整性验证通过后交付。
