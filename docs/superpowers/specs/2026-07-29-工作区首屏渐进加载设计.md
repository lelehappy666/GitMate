# 工作区首屏渐进加载设计

## 目标

页面 10 与页面 11 不再等待全部仓库的本地 Git、GitHub 摘要和 README 请求完成后才呈现数据。首屏先使用有效缓存与本地仓库记录，随后在严格并发上限内逐仓库刷新，并保留取消、错误降级与缓存原子更新语义。

## 根因

`WorkspaceContentService.dashboard` 逐仓库调用 `repositoryContent`，仓库之间完全串行；`repositoryContent` 内又依次等待本地状态、最近提交、在线摘要和 README。`DashboardViewModel` 只接受最终聚合值，仓库墙容器也在完整调用结束后替换整个 ViewModel，因此现有数据无法渐进更新。

## 设计

`WorkspaceDashboardLoading` 新增 `dashboardUpdates` 增量流要求，并为现有测试替身和其他实现提供“调用一次 `dashboard`、发布一次结果”的默认适配。`WorkspaceContentService` 提供真正的增量实现，同时保留 `dashboard`：旧入口消费增量流并返回最后一个快照，保证调用方兼容。

增量流分为两个阶段：

1. 读取一次账户缓存。每个仓库优先采用有效缓存中的本地记录与在线摘要；缓存缺失时读取本地目录记录。此阶段不发起本地 Git 或 GitHub 异步请求，组装完整仓库顺序的首屏快照并立即发布。
2. 使用有界任务组逐仓库调用现有 `repositoryContent`。并发仓库数默认最多为 4，可在测试中注入更小值，且始终限制在 1 至 8。任一仓库完成后按仓库编号替换对应内容，再按输入仓库顺序发布新的完整快照。

生产任务与流终止绑定：消费者取消或提前停止消费时取消生产任务；任务组和 `repositoryContent` 继续向上传播 `CancellationError`。在线摘要仍通过现有 `cache.update` 原子合并，不改变缓存有效期和敏感信息清理规则。

## ViewModel

`DashboardViewModel` 持续消费增量流。每个快照都立即派生页面状态；刷新未结束时保持 `.loading`，流正常结束后进入 `.loaded`。取消恢复加载前状态；首个快照前失败沿用空失败状态；已有快照后的失败保留已呈现数据，只更新失败提示。

`RepositoryWallViewModel` 增加原位更新海报项的入口，不重建 ViewModel，因而搜索、可见性、语言、同步状态和排序条件不会在增量刷新时丢失。页面 11 容器只负责消费同一增量流、构建海报并调用原位更新；该容器改动单独提交。

## 测试

- 首个服务快照在远程请求完成前可取得，并包含缓存/本地记录。
- 并发刷新不超过注入上限，所有仓库最终都被刷新。
- 服务快照按仓库完成顺序渐进发布，同时最终仓库顺序稳定。
- Dashboard 在流结束前写入首屏与后续快照，取消与失败不破坏已有语义。
- 仓库墙原位更新后保留用户筛选状态。
- 运行相关核心测试、完整核心测试运行器、构建和 `git diff --check`。

## 范围

优先修改 `WorkspaceContentService`、`DashboardViewModel`、`RepositoryWallViewModel` 及对应测试。`WorkspaceRootView` 仅修改 `RepositoryWallContainer` 的加载方法和必要初始化，不触碰路由、授权、Onboarding 或运行时依赖。
